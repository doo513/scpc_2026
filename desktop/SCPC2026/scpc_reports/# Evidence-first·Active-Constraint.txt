기본 원칙

각 단계는 새로운 기능만 추가하는 것이 아니라 다음 세 항목을 함께 완료해야 한다.

data contract
implementation
executable invariant tests

각 단계의 테스트를 통과하지 못하면 다음 단계로 넘어가지 마라.

기존 하네스를 즉시 대체하지 말고 새 엔진을 shadow mode로 병렬 실행하라. 새 엔진의 answer와 trace를 기존 엔진 및 공식 dev reference와 비교하고, 해당 단계의 완료 조건을 충족한 영역만 선택적으로 전환하라.

복합 operation의 control 집계 방식

완료 조건

완료 조건

provisional write를 같은 turn의 후속 clause가 참조할 수 있다.
speculative state가 persistent state를 직접 변경하지 않는다.

Step 4. Sub-operation 및 Dependency Graph를 구성하라

절별 evidence를 다음 구조로 묶어라.

SubOperationCandidate
- domain_candidates
- operation_candidates

- target_candidates
- evidence_ids

- write_dependencies
- cancellation_edges
- supersession_edges

dependency graph는 실제 참조 관계가 확인된 경우에만 생성하라.

B가 A의 provisional value를 참조
→ B depends_on A

단순히 문장 순서가 앞선다는 이유만으로 dependency를 만들지 마라.

순환 dependency가 발생하면 임의 순서로 실행하지 말고 해당 component를 unresolved 또는 ask 후보로 표시하라.

완료 조건
독립된 두 operation과 의존하는 두 operation을 구분한다.
rollback 대상과 연쇄 rollback 대상이 graph에서 계산된다.
cycle이 조용히 무시되지 않는다.

후보 상태를 다음처럼 구분하라.

완료 조건

정보 부족 후보가 삭제되지 않고 ask 후보로 남는다.
동일 배열을 permutation해도 후보 집합이 동일하다.
Step 6. Constraint Refinement와 Capability Evaluation을 단방향으로 수행하라

후보별 평가를 다음 순서로 고정하라.

Base Pair
→ BasePlanBlueprint
→ pair-specific Constraint 활성화
→ ConstraintEffect 적용
→ FinalPlanRequirements 도출
→ Capability 검사
→ CandidateState 확정

ConstraintEffect는 다음과 같이 제한을 추가하는 방향으로만 작동하게 하라.

ADD_CONFIRMATION
ADD_REDACTION
FORCE_SUMMARY
LIMIT_DURATION
BLOCK_EXECUTION
RESTRICT_TARGET

후속 단계가 이미 적용된 hard restriction을 해제하지 못하게 하라.

Capability는 최종 출력 plan에 필요한 전체 verb와 resource를 기준으로 검사하라.

각 capability에 source를 명시하라.

PLATFORM_ACTION
INTERNAL_TRANSFORM
CONTROL_FLOW

공식 근거 없이 plan event verb를 INTERNAL_TRANSFORM으로 분류하지 마라.

완료 조건
constraint 적용으로 추가된 safeguard capability까지 평가된다.
executable 후보가 compiler에서 capability 오류를 일으키지 않는다.
같은 입력으로 평가 순서가 달라져도 CandidateState가 변하지 않는다.
Step 7. Authorized Fallback Graph를 평가하고 최종 Bundle을 잠가라

Fallback을 단순히 다음 순위 후보로 취급하지 마라.

허가된 fallback 관계를 다음 구조로 표현하라.

FallbackEdge
- source_candidate
- destination_candidate
- authorization_source
- semantic_preservation
- activation_condition
- reason_code

FallbackEdge는 다음 중 하나의 근거가 있을 때만 생성하라.

현재 사용자의 명시적 대안 지시
공식 policy에 정의된 대체 경로
동일 의미를 보존하는 공식 plan transformation

각 fallback 목적지 후보는 Step 6과 동일한 평가 함수를 통과해야 한다. 축약된 별도 평가 경로를 만들지 마라.

결정 규칙:

실행 가능한 원 후보
→ 원 후보 선택

원 후보 차단 + authorized fallback 1개
→ fallback 선택

authorized fallback 0개
→ hold 또는 ask 원인 판정

authorized fallback 여러 개
→ ask

모든 sub-operation을 선택한 뒤 dependency graph를 적용하라.

선행 operation이 rollback되면 해당 operation의 값을 실제로 참조한 후속 operation만 cascading rollback하라.

그 후 최초이자 마지막으로 DecisionBundle과 SubDecisionIR을 lock하라.

완료 조건
fallback 이후 target이나 operation이 다시 변경되지 않는다.
fallback 목적지가 동일한 constraint/capability 평가를 통과한다.
허가 근거 없는 안전한 대안이 자동 실행되지 않는다.
dependency rollback이 독립 operation까지 제거하지 않는다.
Step 8. Bundle Control·Scope 집계 규칙을 확정하라

복수 sub-operation의 결과를 공식 answer 한 개로 압축하는 규칙을 별도 BundleAggregator로 구현하라.

다음 사례를 공식 dev reference와 guide로 검증하라.

proceed + proceed
proceed + ask
proceed + hold
amend + proceed
의존 operation hold
독립 operation hold

공식 근거가 없는 집계 규칙은 assumption으로 유지하라.

집계 과정에서 sub-operation의 개별 상태를 제거하지 마라. 최종 answer가 하나의 control만 허용하더라도 trace에는 모든 sub-decision을 보존하라.

완료 조건
aggregate control의 근거가 각 sub-decision으로 추적된다.
독립 operation과 의존 operation의 결과가 구분된다.
전체 task control 하나만 보고 부분 commit 여부를 결정하지 않는다.
Step 9. Pure Scope·Policy·Plan Compiler를 구현하라

각 compiler는 lock된 DecisionBundle의 projection만 입력받아야 한다.

원본 prompt, ActionProfile, 원본 record를 다시 조회하지 마라.

PlanBlueprintRegistry는 Step 5의 BasePlanBlueprint와 Step 6의 ConstraintEffect를 동일하게 사용하라.

ScopeCompiler는 다음 의미를 구분하라.

raw
summary
redacted
status_only
none

PolicyCompiler는 active constraint, fallback, safeguard reason을 고유 reason code로 보존하라.

PlanCompiler는 각 sub-decision의 semantic operation을 공식 plan ontology로 변환하고 dependency 순서에 따라 병합하라.

selected operation == terminal verb 문자열을 검사하지 말고 blueprint의 semantic_terminal과 실제 plan 의미를 비교하라.

완료 조건
compiler가 raw 자연어를 재해석하지 않는다.
toggle amend가 dispatch로 변환되지 않는다.
summary/redacted safeguard가 plan과 일치한다.
복수 sub-operation의 plan 순서가 dependency graph와 일치한다.
Step 10. 각 단계의 검증기를 누적하고 Shadow Mode로 전환하라

검증기를 마지막에 새로 만들지 마라. Step 1부터 생성한 invariant를 하나의 종단 validator로 누적하라.

최소 hard gate:

selected pair target == final target
locked operation은 compiler에서 변경되지 않음
active constraint == policy reason
fallback edge == fallback trace
plan capabilities 충족
scope와 safeguard event 일치
dependency order 일치
rollback operation의 terminal event 없음
공식 schema 통과

새 엔진을 기존 엔진과 병렬 실행하라.

비교 대상:

공식 dev reference
legacy output
metamorphic variants
array permutation
counterfactual constraint variants

기존 legacy output과의 불일치는 참고 진단으로만 사용하라. 공식 dev reference와의 mismatch는 release failure로 유지하라.

task ID나 특정 이름에 기반한 예외를 만들지 마라. 의미론적 예외가 필요하면 다음을 모두 포함하는 registry entry로 제한하라.

typed predicate
official evidence
positive examples
counterexamples
paraphrase tests
dataset version
review owner
완료 조건
각 단계 merge 전에 해당 단계 invariant가 통과한다.
신규 구조가 사용되지 않는 장식용 모듈은 ablation test에서 발견된다.
전체 전환 전까지 legacy path를 복구 가능하게 유지한다.

재검토할 때마다 계속 개선점이 생기는 이유

현재는 계속 생기는 것이 정상입니다. 이유는 단순합니다.

지금까지 설계를 대부분 자연어 문장으로 작성하고, 한 번에 한 가지 반례만 대입했기 때문입니다. 자연어 설계에는 다음이 명확히 드러나지 않습니다.

상태 조합 전체
단계 간 입력 의존성
복수 operation
실패와 fallback의 전파
constraint가 plan을 변경하는 경우
부분 성공과 부분 rollback

따라서 하나를 고치면 그 규칙이 다른 규칙과 충돌하는 것이 뒤늦게 발견됩니다.

하지만 이 과정이 무한히 계속될 필요는 없습니다. 지금부터 검토 방법을 바꾸면 빠르게 수렴시킬 수 있습니다.

빠르게 헛점을 줄이는 방법
1. 문장 검토보다 상태표를 먼저 작성

예를 들어 fallback을 산문으로 쓰지 말고 다음 축의 표를 만듭니다.

원 후보 상태
fallback 수
fallback authorization
dependency 여부
정보 추가 가능 여부
→ 최종 결과

가능한 조합을 표로 채우면 누락된 분기가 바로 드러납니다.

2. 핵심 객체마다 불변식을 먼저 작성

코드보다 다음을 먼저 고정합니다.

Final target은 lock 이후 변경되지 않는다.
Fallback 후보도 원 후보와 동일한 evaluator를 통과한다.
Rollback된 operation은 plan에 terminal event를 남기지 않는다.
Policy reason은 반드시 active constraint 또는 fallback trace를 참조한다.

반례가 생길 때 설계 문장 전체를 다시 고치는 대신 어떤 invariant가 부족했는지 추가하면 됩니다.

3. 작은 반례 집합을 고정

최소 20~30개의 적대적 사례를 counterexample suite로 고정합니다.

반드시 포함할 사례:

결제 실행 / 확인 / 공유 / 취소
일정 생성 / 변경 / 확인 / 취소
켜기 / 끄기 / 켜지 말고 끄기
인용된 실행 문장
external 차단 + local fallback
capability 부족
required slot 부족
복수 독립 operation
복수 의존 operation
partial rollback
session anaphora
배열 permutation

새 설계를 수정할 때마다 전체 suite를 다시 대입해야 합니다.

4. 한 번에 전체 도메인을 구현하지 않기

다음 순서의 vertical slice가 효율적입니다.

DISPATCH / LOCAL_UPDATE
→ PAYMENT
→ DEVICE
→ CALENDAR
→ 복합 operation
→ session lifecycle

각 도메인마다 다음 전체 경로를 완성합니다.

parse
→ candidate
→ constraint
→ fallback
→ compile
→ validate

인프라 전체를 먼저 만든 뒤 모든 domain을 한꺼번에 연결하면 헛점이 더 늦게 발견됩니다.

이렇게 하면 구조를 바꾸면서도 어떤 단계에서 결과가 달라졌는지 바로 알 수 있습니다.

최종 결론

재검토할수록 개선점이 계속 나오는 상태가 맞습니다. 하지만 현재까지는 설계가 나빠서만이 아니라, 검토 방식이 산문 중심이었기 때문입니다.

이번 재검토에서 가장 중요한 수정은 다음 세 가지입니다.

단일 FinalDecisionIR
→ DecisionBundle + SubDecisionIR

단순 fallback 후보
→ 명시적 FallbackEdge

선형 capability 평가
→ blueprint → constraint effect → final requirements → capability

이제부터는 새로운 장문의 계획서를 반복해서 다시 쓰기보다:

IR
+ 상태 전이표
+ 불변식
+ counterexample suite

를 기준으로 검토하는 편이 훨씬 빠릅니다. 이 네 가지가 고정되면 추가 개선점은 계속 나오더라도 구조 전체를 다시 뒤집는 수준이 아니라, 누락된 상태나 매핑을 보충하는 수준으로 줄어듭니다.
